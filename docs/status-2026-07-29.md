## 1. Verdict

This is a genuinely well-kept small codebase. All 161 tests pass, `SHELL` is exactly
complete against the tree, `CACHE_VERSION` and its guard assertion are correctly paired,
and the three data-model invariants hold under inspection — the memo invalidation in
particular is airtight by construction rather than by discipline. **No Critical and no
Important defects in shipped behaviour.** The one thing worth attention before more
features land is a test-surface hole rather than a bug: the i18n key families built
dynamically from catalog data (`exercise.columns.${field}`, `exercise.pair.${kind}`,
`exercise.gain.${field}`) are unproven by any test, and roadmap step 5 is the step that
will add a new exercise kind.

What is genuinely well done, briefly: the memo-drop lives in `saveState()`
(`src/state.js`) rather than in each mutator, so a mutator added later *cannot*
forget it — the comment says exactly that, and it is true. `byRecency`
(`src/state.js`) documents the tie it deliberately declines to break, and gives the
reason. `resolveKey` distinguishes "beyond `MAX_SETS`, therefore junk" from "beyond the
current count, therefore hidden" (`src/state.js`) — that distinction is the whole
reason the set stepper is non-destructive, and it is tested from both sides. The `elements`
map is 1:1 with `index.html` with zero drift in either direction.

## 3. Findings

No Critical. No Important defects in shipped behaviour. One Important gap in test coverage.

### Important

**`tests/i18n.test.js` — dynamically-built key families are unproven**

`tests/i18n.test.js` proves two things: exact key parity between locales, and a name
for every `CATALOG` exercise and `GROUPS` entry. It does not prove that the key families
constructed at render time from catalog data exist at all. Those are:

- `exercise.columns.${field}` and `exercise.fields.${field}.{placeholder,aria}` —
  `columnHeadings` and `setRow` in `src/views/day.js`, one per `ENTRY_FIELDS` member
- `exercise.pair.${kind}` — `src/views/day.js`, one per catalog `kind`
- `exercise.gain.${gain.field}` — `setRow` in `src/views/day.js`, one per field `setGain`
  can return

All of these currently resolve in both locales. The hole is what happens next. `t()` returns
the key itself when a lookup misses (`src/i18n/index.js`), so the failure is silent and
visible only in a browser.

*Failure scenario:* roadmap step 5 adds a user-exercise with a third `kind` (or a fifth
entry field — the step's own text contemplates the lookup layer changing). `FIELDS_BY_KIND`
gains an entry; nobody adds `exercise.pair.mobility`. Both locales still have identical key
sets, so parity passes; the new kind is not in `CATALOG`, so the catalog-name test passes.
All 161 tests stay green, and the day view renders the literal string
`exercise.pair.mobility` between the two input boxes.

*Fix:* one test in `tests/i18n.test.js` that walks `ENTRY_FIELDS`, the distinct `kind`s in
`CATALOG`, and `["kg","dist","reps"]`, asserting `t(key) !== key` in every locale. Entirely
in the pure layer, ~12 lines, no new file.

### Minor

**`lastTrainedNote` in `src/views/day.js` — a future timestamp renders a dangling label**

`lastTrainedNote` renders unconditionally once `lastLoggedAt` returns a finite number, but
`formatAge` returns `""` for a timestamp in the future (`src/format.js`). The result is a
`<p>` reading `"Last logged "` / `"Registrado "` with nothing after it.

*Failure scenario:* restore a backup written on a device whose clock ran ahead.
`normalizeEntry` (`src/state.js`) keeps any finite `at` with no upper bound, so the
future timestamp survives import; `lastLoggedAt` returns it; the day view shows the
truncated sentence. The ghost row's age tag takes the same input and degrades correctly —
an empty tag reads as intentional — which is why only this caller is affected.

*Fix:* have `lastTrainedNote` compute the string first and return `null` when it is empty,
matching the rule the function's own comment already states ("an untrained day says so by
having no line").

**`src/app.js` — `day.id` is unguarded on the log screen**

`render()` correctly passes `plan`/`week`/`day` as null when there are no plans, but the
`isLog` branch dereferences `day.id` without a guard. Every path into `screen === "log"` was
traced — `usePlan` (requires a plan) and the Plans back button (the `onBack` `currentView`
passes `renderPlansView`, withheld when
`plan` is falsy) — along with every mutator reachable *from* the log screen, including
import, which sets `screen = "plans"` before rendering (`handleImportFile`). **No failure could be
constructed, so this is a style note, not a bug.** It is worth recording only because
`CLAUDE.md` says any new screen has to hold up with nothing selected, and this is the line
that would not.

**`src/plan.js` — `dayLabel` has no direct test**

Pure, and now the single source of the day's name in four places (chips, day heading, editor
day card, clear-day confirmation) after commit `009b888` consolidated them. Covered only
transitively through `displayName` and `dayNumber`. Cheap to pin: two assertions, named and
unnamed.

**`src/state.js` — `countSlotEntries`'s `week: null` mode has no production caller**

`countDayEntries` is the only caller and always passes a real week; the null-week branch is
reached solely from `tests/state.test.js`. That branch also uses
``key.includes(`|${slotId}|`)`` rather than a positional check, which would false-positive if
an imported plan ever carried a numeric slot id matching a week number. Unreachable today —
app-minted ids are `s-*` — but it is untested API surface with a sharp edge on it.

**`src/views/planEditor.js` and `src/views/day.js` — typographic glyphs
bypass `t()`**

`"−"`, `"+"`, `"–"`, `"↑"`, `"↓"`, `"×"` are hardcoded, and `src/views/plans.js` joins the
summary with a literal `" · "`. Every one has a translated `aria-label` beside it, so nothing
is inaccessible. Noted only because `src/i18n/en.js` routes `exercise.pair` (`"×"`,
`"·"`) through `t()` with the explicit reasoning *"Not language, but it sits in the view, so
it goes through t() like everything else there"* — that reasoning applies equally to the six
glyphs that do not. The inconsistency is in the code, not the docs; no direction is proposed
here, since either one is defensible and it is the author's call.

## 4. Documentation changes

### `CLAUDE.md` — Architecture, Views bullet

**Was:** "They never touch the store's mutators directly except through the callbacks
`app.js` passes in. `app.js` owns all actions, confirmations, and `render()`."

**Now:** "Actions go through the callbacks `app.js` passes in, with one deliberate exception:
`views/day.js` calls `store.setEntryField` itself, because a keystroke has to write through
*without* a `render()` and `app.js` owns `render()`. Everything else — confirmations,
destructive actions, navigation — is `app.js`'s."

**Proof:** in `src/views/day.js`, the `write` callback `setRow` hands `numericField`
(`(value) => store.setEntryField(...)`) and the ghost-row fill call the mutator directly,
with `store` passed into the view. Grep
confirms these are the *only* two such calls in `src/views/`; every other view touches read
methods only. The exception is deliberate and already reasoned about elsewhere in the
codebase — `src/views/fields.js` and `src/views/day.js` both explain that
`render()` must never fire from a text-input handler — so the doc was the thing that had
drifted, not the code.

### `CLAUDE.md` — Style, CSS colour rule

**Was:** "colour is spent in exactly one place, the gain badge (`--gain`). Primary buttons
are a solid ink fill, never a coloured one, and `--focus` is only ever an outline."

**Now:** "the gain badge (`--gain`) is the only colour the design *spends*. Primary buttons
are a solid ink fill, never a coloured one; `--focus` is only ever an outline and `--danger`
only ever text and a border."

**Proof:** `styles/app.css` declares three chromatic tokens — `--gain`, `--danger`,
`--focus`. Its `.btn--danger` rule is `color: var(--danger); border-color:
var(--danger);`, so the Delete buttons are visibly red text. `CLAUDE.md` already carved out
`--focus` but not `--danger`, leaving a claim a stranger disproves by looking at one button.
The operative rule in the CSS header — no accent as a *fill* — is obeyed throughout, so only
the exception list needed completing.

### `README.md` — Backing up your progress

**Was:** "Backups exported by older versions of the app still restore: the file format has

**Now:** "Backups exported before plans became user-editable are rejected as invalid: they

been false since plans landed. The code is right and deliberate; the doc was stale.

## 6. Health of the invariants

- **`SHELL` completeness** — **holding.** 0 missing, 0 stale, verified against `git ls-files`
  independently of the repo's own test.
- **`CACHE_VERSION` + guard assertion** — **holding.** `progression-v10` in `sw.js`,
  `progression-v9` named in the assertion, both moved in `38539a1`.
- **Layering** — **holding, with one documented exception.** `views/day.js` calls
  `store.setEntryField` directly; deliberate, and `CLAUDE.md` now says so. No pure module
  touches the DOM. No view imports the store module for anything but its pure helpers.
- **A slot owns the history** — **holding.** Every destructive path reports before it acts:
  `savePlan`→`countOrphans`, `deletePlan`→`countPlanEntries`,
  `clearDay`→`countDayEntries`, set-stepper→per-set confirm — all four in `src/app.js`.
  `countOrphans(draft)` is computed on the un-normalized draft, but every field the editor can
  produce is already within `normalizePlan`'s bounds (steppers clamp weeks/sets, Add-day is
  disabled at `MAX_DAYS`), so the count cannot understate what `updatePlan` will prune.
- **Records never cross plans; the lookup does, once** — **holding.** Every mutator filters on
  a `${planId}|` prefix. `findPrevious`'s fallback excludes the viewed plan at
  `src/state.js`, and `tests/state.test.js` pins the heavy/light-day case that
  makes it matter.
- **Memo invalidation** — **holding, and structurally so.** `exerciseIndex = null` lives in
  `saveState()` (`src/state.js`), through which all ten state-mutating methods funnel;
  `setPref` correctly bypasses it via `savePrefs`. Tested from both the write and the import
  direction.
- **State is self-consistent** — **holding.** Every field written by every mutator was
  enumerated against `normalizeState`/`normalizePlan`/`normalizePrefs`: all five state fields,
  all six pref keys (grep-confirmed against `setPref` call sites), all five entry fields, and
  every plan/day/slot field are handled. **No unhandled field, so no silent data-loss bug.**
- **Empty state** — **holding.** Traced fresh-install → create → save → Plans → Back → log,
  and delete-last-plan. `activePlan()` falls back correctly, `renderPlansView` withholds Back
  through the `onBack` `currentView` passes it, banners read `entries` and stay hidden. The
  single unguarded dereference is `day.id` in `render()`'s `renderSelectors` call, unreachable
  today (§3).
- **i18n discipline** — **holding for language.** No literal user-facing text; no hand-rolled
  plurals; ordinals are per-locale functions; `parseNumber` accepts a comma unconditionally.
  Six typographic glyphs sit outside `t()` (§3). `pt-BR` has not drifted: parity passes and
  every dynamic key resolves there too.
- **Accessibility conventions** — **holding.** All three screens carry `class="screen-title"`
  with `tabIndex: -1`; `render()` skips the focus move on first paint (`src/app.js`).
  Static markup ↔ `elements` map is 1:1 with zero drift.
- **CSS colour discipline** — **holding as written in the CSS header.** No accent is used as a
  fill or a gradient; `--focus` is outline-only; `--danger` is text and border only.
  `CLAUDE.md`'s summary now names all three tokens.
